# Land Through a Command on Unprotected Bases

Chose a `land` command in `self-merge.sh` over branch protection or a merge
queue for Teloleo and Straylight. Both are private repositories on a free
organization plan, which offers neither. The command runs the landing
procedure of `docs/proposals/parallel-work-design.md` §3: fetch the base,
rebase the head onto its tip when needed, wait for CI on that exact commit,
and merge only if the base hasn't moved. It is now the `self-merge` skill's
merge step. Issue #293 carries the contract.

## Decisions

- **A phase of `self-merge.sh`, not a separate script.** The phase reuses the
  script's PR read, `--repo` pinning, remote validation, lease-push pattern,
  and `OK` / `STOP` / `LOOKUP_FAILED` protocol. Its matrix's `gh` shim tests
  it offline. A second script would duplicate the remote-identity guards.
- **One round per run, over an internal retry loop.** A round can take a full
  CI cycle, and every refusal (conflict, red CI, a moved base) is something
  the agent should see and judge. Rerunning `land` is the retry.
- **A rebase ends the run.** After the lease push, `land` stops `rebased`. The
  agent reads the range-diff, then reruns `check` and `land` with the new
  head. The landing rule merged in PR 297 says a landing check reruns CI but
  doesn't review, so a pushed refresh still needs its diff read. The owner
  rejected landing in one run, which contradicts that rule. The owner also
  rejected waiting for the automated reviewer, which may not run, varies in
  timing, and can pass silently.
- **`merge` stays a phase.** `land` ends by calling it, and it remains the
  direct choice where a required check already enforces the procedure, such
  as Freeside's.
- **No CI is a refusal.** A commit with no check run and no commit status by
  the cap stops `checks-missing`. Only success, neutral, and skipped pass.
  A push that hasn't started CI yet must not read as green.
- **The rebase runs in a temporary detached worktree.** This revises #293's
  assumption that `land` rebases in the worktree holding the head. Git treats
  ignored files as expendable, so an in-place rebase overwrote or deleted
  them in three shapes that review found one at a time (reproduced). The head
  worktree now moves with `checkout --no-overwrite-ignore -B`, which refuses
  every shape and changes nothing. A conflict leaves the branch untouched. A
  refused lease push moves the local branch back, so `check` agrees with the
  forge.
- **The rebase push needs no second confirmation.** Codex's review of PR 300
  asked for a stop or an opt-in flag before it, citing the guardrail that
  confirms a force-push. Rejected: #293 prescribes the lease push, and a lease
  on the reviewed head of the PR's own branch can't drop anyone's work. The
  guardrail now says so, and `--dry-run` shows beforehand whether `land` will
  rebase.
- **A cross-repository head is never rebased.** `land` would have to push to
  another repository's branch, so it stops `not-on-tip` for its author.
- **The base reread sits before the auto-delete refresh.** Merge already keeps
  zero forge reads between that refresh and the merge, to protect fork
  branches from a late auto-delete change. The base check gives up one read of
  window instead, since a moved base costs a retry, not lost work.

## Refute-First Findings

A fresh-context reviewer tried to break the change before commit. Confirmed
and fixed:

- **Ignored files.** An in-place rebase overwrote an ignored file at a path
  the base started tracking (reproduced). Codex's review of PR 300 then found
  a path the head stopped tracking and a directory the base replaced with a
  file. A path-list check kept missing shapes, so the rebase moved out of the
  head worktree (see Decisions).
- **Guard order.** The force-push ran before the consumer and queue guards,
  so it could rewrite a branch another PR heads or stacks on. They now run
  first.
- **Retarget.** A retarget during the CI wait went unseen. The final PR read
  now compares the base name.
- **Empty rebase.** A branch whose commits were all upstream rebased to the
  base tip and would have been pushed as the head (reproduced). It now stops
  `rebase-failed` and restores the branch.
- **Partial CI.** One green read can precede a slower workflow's checks, so a
  pass needs two consecutive green reads. Codex's review of PR 300 found
  that a first green read at the cap still passed; it now stops
  `checks-pending`.

A second refute pass on the redesigned rebase found three more defects, now
fixed. Submodule recursion skipped `--no-overwrite-ignore`, and truncated
refusal text hid the ignored-file match. A failing hook or a stale ref lock
misreported the move. Declined: an unwritable worktree directory, where git
exits 0 and the pushed commit is still right, and a pre-push hook that blocks
the restore, which is reported honestly.

Disproved by a check: a stale lease being accepted, and the `--` forms of
`git worktree` and `git push` failing (both run on git 2.50); the combined
status's `pending` with no statuses reading as pending CI (a live read of
both repositories returned it, and the count gates it).

Declined: a separate wait cap for the PR head after the push. It reuses the
CI cap, so `--ci-cap-minutes 0` after a rebase ends `LOOKUP_FAILED pr-head`,
which is an accurate report for a run told not to wait.

## Accepted Risk

The final base read and the merge are separate API calls, so a merge that
lands between them goes unseen. The proposal's §2.6 accepts this while one
person starts every merge. The rebased diff gets the agent's own range-diff
read, not an automated review, so a reviewer's finding on it can still
arrive after the merge.

Revisit when landings crowd each other: a repository-wide lock would close
the window. Also revisit if either repository moves to a plan with branch
protection, where a required check can replace the command.
